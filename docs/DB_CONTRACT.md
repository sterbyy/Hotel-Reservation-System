# Контракт backend с PostgreSQL

Это описание действующих ORM-моделей и миграций локального прототипа. Ревизии `0001_prototype`, `0002_booking_lifecycle` и валюта **KZT** предварительные. Схема и порядок переноса требуют проверки владельцем БД.

## Таблицы, поля и ограничения

Приложение обращается к таблицам без указания схемы. Их разрешение зависит от `search_path` подключения. Столбцы имеют `NOT NULL`, кроме явно отмеченных.

### `rooms`

| Столбец | Тип PostgreSQL | Назначение и ограничения |
| --- | --- | --- |
| `id` | `integer` | Первичный ключ, значение берётся из последовательности (`SERIAL` в DDL миграции) |
| `name` | `varchar(120)` | Название номера |
| `description` | `text` | Описание для карточки |
| `category` | `varchar(80)` | Категория для выдачи и карточки |
| `capacity` | `integer` | Вместимость, `ck_rooms_capacity` проверяет `capacity > 0` |
| `nightly_rate` | `numeric(10,2)` | Тариф за ночь, `ck_rooms_nightly_rate` проверяет `nightly_rate >= 0` |
| `amenities` | `text[]` | Список удобств, по умолчанию пустой массив `'{}'::text[]`. Для API элементы массива должны быть строками |

### `bookings`

| Столбец | Тип PostgreSQL | Назначение и ограничения |
| --- | --- | --- |
| `id` | `integer` | Первичный ключ, значение берётся из последовательности (`SERIAL` в DDL миграции) |
| `room_id` | `integer` | Внешний ключ на `rooms.id`, стандартное действие `NO ACTION` при удалении или изменении ключа номера |
| `check_in` | `date` | Дата начала проживания включительно |
| `check_out` | `date` | Дата окончания эксклюзивно, `ck_bookings_dates` проверяет `check_out > check_in` |
| `guests` | `integer` | Число гостей, `ck_bookings_guests` проверяет `guests > 0` |
| `status` | `varchar(16)` | Сервис создаёт бронь с `PENDING`. `ck_bookings_status` допускает `PENDING`, `CONFIRMED` и `CANCELLED` |
| `total_price` | `numeric(18,2)` | Сумма на момент записи, `ck_bookings_total_price` проверяет `total_price >= 0` |
| `access_token_hash` | `bytea`, допускает `NULL` | SHA-256 от случайного токена с 256 битами энтропии. `ck_bookings_token_hash` проверяет длину ненулевого значения в 32 байта |

Брони из ревизии `0001` сохраняют статус `PENDING` и получают `NULL` в `access_token_hash`, поскольку секретный токен тогда не выдавался. Проверка доступности опирается на статус и даты, поэтому эти записи продолжают удерживать свои интервалы. Для новых методов управления условие совпадения хеша с `NULL` не выполняется, и они возвращают `404`. PostgreSQL, прокси и трассировка приложения должны исключать логирование секретного заголовка и значений SQL-параметров с хешами.

Индекс `ix_bookings_room_dates` — обычный B-tree по `(room_id, check_in, check_out)`. Он помогает искать пересечения. Ограничения уникальности периода и исключающего ограничения на уровне БД пока нет.

### `payments`

| Столбец | Тип PostgreSQL | Назначение и ограничения |
| --- | --- | --- |
| `booking_id` | `integer` | PK и FK на `bookings.id` со стандартным действием `NO ACTION`. Для каждой брони хранится максимум одна строка |
| `status` | `varchar(16)` | `ck_payments_status` допускает `FAILED`, `SUCCEEDED` и `REFUNDED` |
| `refunded_amount` | `numeric(18,2)`, допускает `NULL` | `ck_payments_refund` требует сумму от нуля для `REFUNDED` и `NULL` для остальных статусов |

До первой попытки строки платежа нет. Повтор после отказа может обновить `FAILED` до `SUCCEEDED`. Таблица хранит последнее состояние, без отдельного журнала attempts. Сумма успешного платежа определяется по `bookings.total_price`. Полный возврат сохраняет эту же сумму в `refunded_amount`. Переходы между таблицами проверяются сервисом.

## Доступность и параллельная запись

При поиске номер должен вмещать всех гостей. Периоды пересекаются только при совпадении `room_id` и одновременном выполнении обоих условий.

```sql
existing.check_in < requested.check_out
AND existing.check_out > requested.check_in
```

Граница периода — `[check_in, check_out)`. Номер занимают `PENDING` и `CONFIRMED`. Статус `CANCELLED` освобождает номер, а срок действия `PENDING` пока не ограничен.

Все три операции записи начинают с блокировки строки номера в транзакции `READ COMMITTED`. Создание проверяет вместимость и пересечения отдельным запросом после блокировки, затем вставляет новую бронь. Оплата и отмена сначала находят номер по ID брони и хешу токена и блокируют только строку `rooms` через `FOR UPDATE OF rooms`. Следующим запросом они повторно проверяют номер и токен и блокируют существующую строку `bookings`. После этого читают платёж и фиксируют изменения одной транзакцией.

Порядок для внешних писателей — `rooms → bookings → payments`. Он сериализует изменения даже для разных броней одного номера. Если отмена получает блокировку первой, последующее создание может занять освобождённый период. Если создание проходит первым, оно увидит активную бронь и получит `409`. После отмены повторный запрос увидит `CANCELLED` и вернёт сохранённое состояние без второго вызова возврата. Observer запускается после commit. Его события не сохраняются в БД.

## Тариф и сумма

Тариф считывается из заблокированной строки номера. Python рассчитывает `total_price = nightly_rate × (check_out - check_in).days` с помощью `Decimal` и сохраняет результат в `bookings.total_price`. Изменение тарифа номера не пересчитывает сохранённые суммы. Валюта **KZT** обозначена на уровне контракта прототипа. Столбца валюты в текущей миграции нет.

## Миграции и сверка

- [0001_prototype](../migrations/versions/0001_prototype.py) создаёт `rooms`, затем `bookings`, ограничения и индекс. Её `downgrade` удаляет обе таблицы вместе с данными.
- [0002_booking_lifecycle](../migrations/versions/0002_booking_lifecycle.py) добавляет nullable-хеш, расширяет допустимые статусы и создаёт `payments`. Существующие брони, статусы и цены сохраняются. Откат ревизии блокируется при наличии новых хешей, расширенных статусов или платежей.

Alembic хранит ревизию в `alembic_version`. Миграции не добавляют пробные данные. Перед переносом `0002` владелец БД должен проверить время и влияние блокировок DDL при расширении ограничения на таблице `bookings`.

Укажите `DATABASE_URL` отдельной пустой локальной или тестовой БД в переменной процесса или локальном `.env`. Используйте драйвер `postgresql+psycopg`. Выполните из корня репозитория после установки зависимостей.

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic check
```

На общей БД используйте согласованные миграции команды. Для сверки на тестовой копии подключитесь через `psql` и проверьте реальные типы, значения по умолчанию, выражения ограничений и индекс.

```sql
SHOW search_path;
\d+ rooms
\d+ bookings
\d+ payments
SELECT version_num FROM alembic_version;
```

Последний запрос применим к БД с Alembic. `alembic check` проверяет различия, которые умеет обнаруживать автогенерация Alembic. Выражения `CHECK` и значения по умолчанию сверяйте отдельно. [Документация Alembic о сравнении схем](https://alembic.sqlalchemy.org/en/latest/autogenerate.html#running-alembic-check-to-test-for-new-upgrade-operations)

## Решения команды перед подключением

- Подтвердить схему PostgreSQL, имена таблиц и столбцов, типы и генерацию ID, внешний ключ и способ хранения категории и удобств. Если ID общей БД выходят за диапазон `integer`, согласовать изменение API с React.
- Подтвердить валюту KZT или другую валюту, точность тарифа и суммы, правило расчёта за ночь и сохранение цены брони.
- Подтвердить `bytea` для хеша, правила для существующих броней с `NULL`, разделение статусов брони и платежа и правило одной платёжной строки на бронь.
- Подтвердить активные статусы, правило смежных дат, UTC для расчёта порога отмены и условия возврата. Определить все процессы записи броней и общий порядок блокировок.
- Согласовать владельца миграций, окно переноса, `search_path` и права runtime-роли. Нужны чтение таблиц, вставка в `bookings` с получением сгенерированного ID, доступ к последовательности, обновление статуса брони и вставка и обновление `payments`. Блокировка `rooms` через `SELECT ... FOR UPDATE` требует права `UPDATE` хотя бы на один столбец этой таблицы. [Документация PostgreSQL о правах SELECT](https://www.postgresql.org/docs/18/sql-select.html)

### Варианты для броней без токена

- Сохранить интервалы и историю до решения владельца БД. Будущая `PENDING` продолжит блокировать пересекающиеся даты. Когда поиск касается периода после её выезда, она уже не влияет на выдачу.
- Если гостю нужно управлять старой бронью, согласовать отдельную аудируемую процедуру проверки владельца. После подтверждения можно выдать новый случайный токен по доверенному каналу и хранить только его хеш. В текущей схеме нет данных для проверки владельца. Нужен подтверждённый источник вне этих таблиц.
- Если старый интервал больше не должен занимать номер, владелец БД и представитель бизнеса могут пересмотреть конкретную бронь и согласовать ручное изменение статуса с аудитом и тем же порядком блокировок. Автоматической отмены, удаления и массовой выдачи токенов нет.

## Предложения на согласование

- Если в `bookings` будут писать несколько сервисов, рассмотреть исключающее ограничение PostgreSQL по `room_id` и диапазону дат `[)`. Перед отдельной миграцией проверить существующие записи, возможность использования `btree_gist` и сохранение ответа API `409`.
